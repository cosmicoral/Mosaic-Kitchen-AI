# Authentication Design

Server-side session authentication for the Mosaic Kitchen API. This document
explains what each piece does and, more importantly, why it was built this way.

## Why sessions and not JWT

A JWT is self-contained: the server signs a token, hands it to the client, and
verifies the signature on each request without touching a database. That is
attractive for horizontally scaled, stateless services, but it has one property
that matters here — **a JWT cannot be revoked before it expires**. Logging a
user out, banning an account, or responding to a stolen token all require extra
machinery (short expiry plus refresh tokens, or a server-side denylist, which
reintroduces the database lookup JWT was supposed to avoid).

Sessions invert that trade-off. Every authenticated request costs one indexed
primary-key lookup, and in exchange revocation is a `DELETE`. For an app of
this size the lookup is irrelevant and the control is worth having.

The secondary reason is storage. The common JWT pattern puts the token in
`localStorage`, which is readable by any JavaScript running on the page — one
XSS bug and the token is gone. A session id lives in an `HttpOnly` cookie that
JavaScript cannot read at all.

## Request flow

```
POST /api/auth/login
  → routes/auth.js          match URL, apply rate limiter
  → controllers/authController.js   read req.body, shape HTTP response
  → services/authService.js         business rules: validate, compare, issue session
  → repositories/*.js               SQL only
  → db/pool.js                      connection pool
  → Neon Postgres
```

Each layer knows only about the one below it:

- **Controllers** know about HTTP (status codes, cookies, `req`/`res`) and
  nothing about SQL.
- **Services** know about business rules and nothing about HTTP. This is why
  they throw tagged errors (`error.code = 'EMAIL_TAKEN'`) instead of returning
  status codes — the controller translates those into 409, 400, 401.
- **Repositories** know about SQL and nothing about business rules. Swapping
  Postgres for something else would touch only this layer.

The practical payoff: services are testable without spinning up an HTTP server,
and adding a second client (an iOS app) requires no changes below the
controller.

## Schema

```sql
CREATE TABLE users (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email         TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE sessions (
  id         TEXT PRIMARY KEY,
  user_id    UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  expires_at TIMESTAMPTZ NOT NULL
);

CREATE INDEX idx_sessions_user_id    ON sessions(user_id);
CREATE INDEX idx_sessions_expires_at ON sessions(expires_at);
```

Decisions worth defending:

**`users.id` is a UUID, not a serial integer.** Sequential ids are guessable.
If a user id ever reaches a URL or an API response, `/users/42` invites someone
to try `/users/43`. UUIDs cost 16 bytes instead of 4 and remove the entire
class of enumeration problem.

**`sessions.id` is `TEXT` with no default.** The value is generated by the
application (`crypto.randomBytes(32)`), not the database, because the same
value has to be written into the `Set-Cookie` header in the same request.
It must be unpredictable: a guessable session id is an account takeover.

**`ON DELETE CASCADE` on the foreign key.** Deleting a user automatically
deletes their sessions. Without it the database would refuse the delete, or —
worse, if the constraint were missing entirely — leave sessions pointing at a
user that no longer exists.

**`TIMESTAMPTZ`, never `TIMESTAMP`.** `TIMESTAMPTZ` normalises to UTC on write
and converts on read. Plain `TIMESTAMP` stores a wall-clock reading with no
timezone, which silently breaks the moment a server, a developer, and a user
are in different zones.

**Both indexes are explicit.** Postgres indexes primary keys and unique columns
automatically but *not* foreign keys. `sessions(user_id)` supports "log this
user out everywhere"; `sessions(expires_at)` supports the expiry filter on
every authenticated request and the cleanup job.

## Password storage

`bcrypt` with a cost factor of 12.

Plain hashes (MD5, SHA-256) are designed to be fast — modern GPUs compute
billions per second, which is exactly what an attacker with a leaked table
wants. bcrypt is deliberately slow and the slowness is tunable: each increment
of the cost factor doubles the work. Cost 12 takes a few hundred milliseconds,
unnoticeable during login, ruinous for brute force.

bcrypt also generates and embeds a random **salt** per hash. Two users with the
password `hunter2` get different stored values, which defeats precomputed
rainbow tables. Because the salt is encoded in the output string, verification
needs no separate salt column — `bcrypt.compare` reads it back out.

Stored format: `$2b$12$<22-char salt><31-char hash>`.

Note the 72-byte limit: bcrypt silently truncates longer input. The service
rejects passwords over 200 characters rather than accept one whose tail is
ignored.

## Session lifecycle

**Creation** (`authService.startSession`)

```js
crypto.randomBytes(32).toString('hex')   // 256 bits of entropy, 64 hex chars
```

`crypto.randomBytes` is a cryptographically secure PRNG. `Math.random()` is
not — it is seeded predictably and is never acceptable for security tokens.

Expiry is 30 days, written to the database and mirrored in the cookie's
`Max-Age` so browser and server agree.

**Verification** (`sessionRepository.findActiveWithUser`)

```sql
SELECT s.id, s.expires_at, u.id AS user_id, u.email, u.created_at AS user_created_at
  FROM sessions s
  JOIN users u ON u.id = s.user_id
 WHERE s.id = $1 AND s.expires_at > now()
```

Two deliberate choices:

1. **The expiry check is in SQL, not JavaScript.** An expired session is simply
   never returned, so no caller can forget to check. It also uses the
   *database* clock — with multiple app servers, their system clocks may drift,
   but there is only one database.
2. **A `JOIN` instead of two queries.** One round trip to Neon instead of two,
   on the hottest path in the application.

**Destruction** — `DELETE FROM sessions WHERE id = $1`, plus a `Set-Cookie`
with an expiry in 1970 (the standard way to instruct a browser to drop a
cookie; HTTP has no explicit delete).

**Cleanup** — `scripts/cleanup-sessions.ts` removes expired rows. They are
already unusable thanks to the SQL filter; this only stops unbounded growth.
Intended to run as a daily cron.

## Cookie flags

```js
{
  httpOnly: true,
  secure:   isProduction,
  sameSite: isProduction && COOKIE_SAMESITE === 'none' ? 'none' : 'lax',
  maxAge:   30 days,
  path:     '/',
}
```

- **`httpOnly`** — `document.cookie` cannot see it. An XSS payload can still
  act as the user while they are on the page, but it cannot exfiltrate the
  session for later reuse.
- **`secure`** — the cookie is only sent over HTTPS. Off in development because
  localhost is plain HTTP and the cookie would otherwise never be sent at all.
- **`sameSite`** — controls whether the cookie rides along on cross-site
  requests, which is the CSRF defence. `lax` in development (frontend and API
  are both `localhost`). In production, if the API and frontend sit on
  different registrable domains, this must be `none`, which the spec only
  permits together with `secure: true`.

If the frontend and API end up on subdomains of one domain
(`app.example.com` / `api.example.com`), `sameSite: 'lax'` works and is
stronger — worth doing at deploy time.

## Attack-specific mitigations

**Timing-based account enumeration.** The obvious login implementation returns
early when the email is unknown, skipping bcrypt. That makes the "no such user"
response measurably faster than "wrong password", letting an attacker discover
which addresses are registered. The fix runs a comparison either way:

```js
const passwordMatches = await bcrypt.compare(
  password,
  user ? user.password_hash : DUMMY_HASH
);
```

`DUMMY_HASH` is a hash of random bytes computed at startup — nothing can match
it, and both paths cost the same.

The response body carries the same defence: an unknown email and a wrong
password both return `401 Invalid email or password`. Signup necessarily leaks
this (409 on a taken email) — that is unavoidable without an email-verification
flow, and it is a deliberate usability trade-off.

**Brute force and credential stuffing.** `express-rate-limit`, 10 attempts per
IP per 15 minutes on auth routes, 300 globally. `skipSuccessfulRequests` means
only failures consume the budget, so someone behind a shared NAT is not locked
out by a stranger's typos. Rate limiting matters more than usual here because
each attempt costs a deliberately expensive bcrypt computation — unlimited
attempts are a CPU exhaustion vector, not just a guessing one.

**SQL injection.** Every query uses parameter placeholders:

```js
pool.query('SELECT ... WHERE email = $1', [email]);
```

The driver sends statement and values separately; Postgres parses the statement
first, so a value can never be interpreted as SQL. This is structural, not
escaping — there is no way to construct input that escapes it. String
interpolation into SQL appears nowhere in the codebase.

**CORS with credentials.** The specification forbids
`Access-Control-Allow-Origin: *` together with
`Access-Control-Allow-Credentials: true`. Allowed origins come from the
`CORS_ORIGINS` environment variable. Requests with no `Origin` header (curl,
native mobile clients) are allowed through — they are not subject to the
browser's same-origin policy, so blocking them protects nobody.

Worth being precise about: CORS protects *users* from malicious sites reading
their authenticated responses. It does not protect the *API* — any non-browser
client ignores it entirely. Server-side protection is authentication,
authorisation, and rate limiting.

**Assorted.** `helmet()` sets defensive response headers. `express.json({ limit:
'1mb' })` caps body size so one large payload cannot exhaust memory. Errors are
logged server-side but responses carry generic messages, so internal details
never reach a client.

## Endpoints

| Method | Path                 | Auth | Success | Notes |
| ------ | -------------------- | ---- | ------- | ----- |
| POST   | `/api/auth/signup`   | –    | 201     | Creates a session; 409 if the email is taken, 400 on validation failure |
| POST   | `/api/auth/login`    | –    | 200     | 401 on bad credentials |
| POST   | `/api/auth/logout`   | –    | 204     | Idempotent; succeeds with no session |
| GET    | `/api/auth/me`       | ✓    | 200     | 401 without a valid session |

`requireAuth` attaches `req.user` and is the single place route protection is
enforced. Any future protected route mounts behind it.

Signup issues a session immediately, so a new user is logged in without a
second round trip.

## Deployment checklist

- `NODE_ENV=production` — enables `secure` cookies and `trust proxy`.
- Leave `COOKIE_SAMESITE` unset for `app.example.com` + `api.example.com`;
  set it to `none` only when the frontend is on a different registrable domain.
- `CORS_ORIGINS` — the real frontend origin(s).
- `trust proxy` is required behind Railway/Render/Fly/nginx. Without it every
  request appears to originate from the proxy and one visitor exhausts the rate
  limit for everyone.
- Switch `DATABASE_URL` to Neon's **pooled** connection string.
- Schedule `scripts/cleanup-sessions.ts` daily.

## Known gaps

- **No email verification.** Any address can be registered without proving
  ownership.
- **No password reset.** The forgot-password screen is not wired to anything;
  a real flow needs single-use expiring tokens and an email provider.
- **No account lockout.** Rate limiting is per-IP, so a distributed attack
  against one account is not slowed. Per-account failure counting would close
  this.
- **No CSRF token.** `sameSite` covers the common cases; a cross-site
  deployment forced onto `sameSite: 'none'` would need real CSRF tokens.
- **No structured logging.** `console.error` is fine locally; production wants
  levelled, redacted, aggregated logs.

## Sign in with Google

Built on `openid-client` v6 directly rather than a wrapper.

- PKCE, `state` and `nonce` are generated per attempt and held in one short-lived `HttpOnly` cookie
- Identities are keyed on `(provider, sub)`, **never on email**. A provider can change the email attached to an account; the subject identifier is the stable one. Keying on email is how account-takeover bugs happen
- `password_hash` is nullable, because an account that arrived through Google has no password. Every read of it handles `null` rather than assuming a string
- Sign in with Apple is deliberately not built yet — it needs a paid Apple Developer account and a verified domain, neither of which exists

### Why identities are keyed on `(provider, sub)`

A provider can change the email attached to an account, and two providers can
report the same email for different people. The subject identifier is the only
stable, provider-scoped key. Keying on email is how account-takeover bugs
happen: sign up with a provider, have it assert an email that already exists
locally, and inherit the existing account.

`password_hash` is nullable because an account that arrived through Google has
no password. Every read of it handles `null` rather than assuming a string —
including the change-password route, which refuses rather than pretending.

## Account and data rights

UK GDPR gives people a right to a copy of their data and a right to have it erased. Both are built, because a product taking UK household data cannot ship without them.

- **Export** returns everything the account owns — profile, pantry, meal plans, shopping list — as a JSON download, in the shape it is stored. Passwords and session ids are excluded: those are credentials, not personal data anyone needs back
- **Deletion** is irreversible and says so. It requires the account's own email address typed exactly, which a mis-click cannot produce. Stripe is cancelled **before** the row is deleted, because the delete cascades the subscription record away and there would be no id left to cancel — the account would be gone and the card would keep being charged
- If Stripe is unreachable the account is still deleted and the failure is logged as `URGENT`. Holding a legal right hostage to a third party's uptime is the worse of the two options; a subscription cancelled by hand the next morning is the better one
- **Changing a password** works only where there is one to change. An account created through Google has `password_hash IS NULL`, and the page says why rather than offering a form that cannot work. *Setting* a first password on such an account is refused: it adds a second way in, and doing that silently from a session is a takeover path

### Why setting a first password is refused

Adding a password to an account that only had Google is adding a **new way
in**, and anyone holding a stolen session could do it silently. That needs
confirmation to the registered address, which needs a verified sending domain
that does not exist yet. The route refuses and says why, rather than quietly
being a takeover path.
